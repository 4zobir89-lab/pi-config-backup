## الورك فلو الإلزامي

### ❌ ما لا تفعله أبداً:

```
- لا تكتب كوداً مباشرة بدون تخطيط
- لا تنشئ ملفات بدون PRD أو plan
- لا تتجاوز اختبارات TDD
- لا تكتب دوال > 50 سطر
- لا تكتب ملفات > 800 سطر
- لا تستخدم hardcode
- لا تتجاوز 4 مستويات تغوص
```

### ✅ ما تفعله دائماً:

```
1. اسأل أسئلة التوضيح أولاً
2. أنشئ PRD/plan قبل التنفيذ
3. اكتب اختبارات أولاً (TDD)
4. استخدم الوكلاء المتخصصين
5. راجع الكود قبل التسليم
6. استخدم Conventional Commits
```

## الخطوة 1: التخطيط (Planner Agent)

**لأي مهمة معقدة:**

```markdown
## المطلوب من planner agent:

1. نظرة عامة على المشروع
2. تقسيم المهام إلى خطوات صغيرة
3. تحديد التبعيات
4. تحديد ملفات الكود المتأثرة
5. تحديد الاختبارات المطلوبة
6. خطة التنفيذ التفصيلية
```

**أمثلة:**
- صمم صفحة هبوط → planner أولاً
- أضف نظام مصادقة → planner أولاً
- أصلح خللاً معقداً → planner أولاً

## الخطوة 2: الاختبارات أولاً (TDD)

**الورك فلو الإلزامي:**

```markdown
## دورة TDD (إلزامي)

1. RED    → اكتب اختباراً (يفشل)
2. GREEN  → اكتب أقل كود ينجح
3. REFACTOR → حسّن مع الحفاظ على التغطية
```

**القواعد:**
- لا تكتب كوداً بدون اختبار
- تأكد من فشل الاختبار أولاً
- اكتب أقل كود ينجح
- حافظ على تغطية 80%+

**أنواع الاختبارات المطلوبة:**
- Unit Tests — دوال وأدوات منفردة
- Integration Tests — API + قواعد بيانات
- E2E Tests — تدفقات مستخدم حرجة

## الخطوة 3: جودة الكود

### المقاييس الإلزامية:

```markdown
## جودة الكود (إلزامي)

- دوال صغيرة (<50 سطر)
- ملفات مركزة (<800 سطر)
- لا تغوص عميق (>4 مستويات)
- معالجة أخطاء في كل مستوى
- لا قيم hardcode
- معرفات مقروءة وواضحة
```

### مبادئ KISS/DRY/YAGNI:

```markdown
## KISS - Keep It Simple
- ابسط حل يعمل فعلاً
- لا تuss التعقيد غير الضروري

## DRY - Don't Repeat Yourself
- لا تكرر نفس الكود
- استخدم الدوال والأدوات

## YAGNI - You Aren't Gonna Need It
- لا تبني ميزات لم تطلب بعد
- ابدأ البسيط وحسّن لاحقاً
```

## 🧠 القاعدة الذهبية #7: إدارة السياق (Context Budget)

### إلزامي لكل جلسة

```markdown
## إدارة السياق (إلزامي)

1. **قياس السياق أولاً** - قبل أي مهمة كبيرة، تحقق من حجم السياق المتاح
2. **ضغط ذكي** - استخدم `/compact` عند نقاط الانقطاع الطبيعية
3. **Context Window Budget**:
   - < 30% متبقي → استخدم `/compact` فوراً
   - < 15% متبقي → توقف عن المهام الجديدة واسأل المستخدم
   - < 5% متبقي  → استخدم `/clear` وابدأ جلسة جديدة
4. **لا تحمل مهارات غير ضرورية** - المهارات تستهلك سياقاً
5. **استخدم Strategic Compacts** - كل 5-10 تبادلات مهمة
```

**مستوحى من:** jcode's compaction engine و memory budget

## 🐝 القاعدة الذهبية #8: تنسيق الوكلاء المتعددين (Swarm)

### عند الحاجة لأكثر من وكيل

```markdown
## Swarm Coordination (إلزامي للمهام المعقدة)

### متى نستخدم سوَرْم:
- مهمة تحتاج 3+ خطوات مستقلة
- مهمة تحتاج تحليلات متعددة (أمن + أداء + جودة)
- بناء مشروع كامل (Frontend + Backend + DB)

### كيف:
1. **قسّم المهمة** إلى وحدات مستقلة
2. **شغّل بالتوازي**:
   - وكيل 1: Backend API
   - وكيل 2: Frontend UI
   - وكيل 3: Database Schema
3. **قسّم العمل**:
   - استخدم worktrees or branches منفصلة
   - لا تشتغل على نفس الملف مع وكيل آخر
4. **ادمج النتائج**:
   - راجع التغييرات من كل وكيل
   - تأكد من عدم وجود تعارضات

### هيكل التنسيق:
- **منسّق (Coordinator)**: الوكيل الرئيسي يوزع المهام
- **عمال (Workers)**: وكلاء متخصصون ينفذون
- **جامع (Merger)**: يجمع النتائج ويراجعها

### قواعد السوَرْم:
- لا وكيل يشتغل على ملف يشتغل عليه آخر
- توثيق كل خطوة كتابياً
- اختبار كل وحدة قبل الدمج
```

**مستوحى من:** jcode's swarm architecture و task graph

## ⚡ القاعدة الذهبية #12: كفاءة الأدوات (Tool Efficiency)

### استخدم الأدوات بذكاء

```markdown
## Tool Efficiency (إلزامي)

### استراتيجيات:
1. **Batch Operations**: استخدم edit مع edits[] متعددة بدلاً من edit+edit+edit
2. **قراءة ذكية**: اقرأ headers وهياكل الملفات أولاً، ثم الأجزاء المهمة
3. **Cache-aware**: تذكر ما قرأته مؤخراً - لا تعيد قراءة نفس الملف
4. **Context-aware Grep**:
   - استخدم grep مع --context لإظهار السياق
   - اقرأ أسماء الدوال والهياكل أولاً

### لا تفعل:
- لا تقرأ ملفاً كاملاً إذا كنت تحتاج 10 أسطر فقط
- لا تكتب اختبارات متطابقة
- لا تستخدم أدوات معقدة لمهام بسيطة

### نصائح:
- `rg -n` مع context numbers
- `fd` بدلاً من `find` للسرعة
- استخدم `gh` للبحث قبل الكود
```

## 📐 القاعدة الذهبية #13: بنية البرومبتات المحكمة (Prompt Architecture)

### استخدم XML Tags للبرومبتات

مستوحى من Codex Plugin for Claude Code، استخدم هذه البنية المنظمة للبرومبتات:

```xml
<!-- الهيكل الأساسي للبرومبت -->
<task>
  صِف المهمة بالضبط: ما الذي تريد تحقيقه، في أي سياق، وما هي الحالة النهائية المطلوبة.
  لا تترك مجالاً للتفسيرات الفضفاضة.
</task>

<structured_output_contract>
  حدد شكل الإخراج بالضبط.
  مثلاً: 1. السبب الجذري 2. الأدلة 3. الخطوة التالية الآمنة
  لا تقبل إجابات فضفاضة.
</structured_output_contract>

<default_follow_through_policy>
  ماذا أفعل بشكل افتراضي؟ هل أكمل حتى النهاية؟ هل أسأل إذا كان هناك غموض؟
</default_follow_through_policy>

<verification_loop>
  قبل إنهاء المهمة، تحقق من أن النتيجة تطابق المتطلبات.
  إذا فشل التحقق، راجع الحل بدلاً من تسليم المسودة الأولى.
</verification_loop>

<grounding_rules>
  استند في كل ادعاء إلى السياق المقدم أو مخرجات الأدوات.
  لا تقدم استنتاجات كحقائق.
  إذا كانت نقطة ما مجرد افتراض، ضع علامة واضحة عليها.
</grounding_rules>

<action_safety>
  حافظ على نطاق التغييرات محدوداً بالمهمة المذكورة.
  تجنب إعادة الهيكلة أو التنظيف غير المرتبط.
</action_safety>

<missing_context_gating>
  لا تخمن معلومات مفقودة عن المستودع.
  إذا كان السياق المطلوب غير موجود، احصل عليه بالأدوات أو اذكر بالضبط ما لا يزال مجهولاً.
</missing_context_gating>
```

**قواعد البناء:**
1. استخدم XML tags فقط للمهام المعقدة (3+ خطوات)
2. المهام البسيطة لا تحتاج tags
3. اختر الأصغر من العقود (contracts) التي تفي بالغرض
4. <structured_output_contract> للشكل المحدد، <compact_output_contract> للنثر المختصر
5. أضف <dig_deeper_nudge> للمراجعات الأمنية
6. أضف <research_mode> + <citation_rules> للبحث

**مستوحى من:** Codex Plugin's GPT-5.4 Prompting skill

## 🚪 القاعدة الذهبية #14: بوابة الإيقاف (Stop Review Gate)

### مراجعة إلزامية قبل إنهاء الجلسة

```markdown
## Stop Review Gate (إلزامي للجلسات التي تحتوي تغييرات)

### متى:
- بعد كل turn فيه تغييرات كود
- قبل إعلان اكتمال المهمة
- بعد تعديل ملفات حساسة

### ماذا:
1. راجع آخر turn فقط (وليس كل التغييرات)
2. تحقق: هل التغيير صحيح؟ هل هناك ثغرات؟
3. قرّر:
   - ALLOW: إذا التغيير سليم أو لا يوجد تغيير في هذا الـ turn
   - BLOCK: إذا وجدت مشكلة تمنع الشحن

### معايير BLOCK:
- تغيير يكسر وظيفة موجودة
- ثغرة أمنية واضحة
- عدم معالجة edge cases (empty state، retries، stale state)
- تصميم خاطئ يسبب مشاكل في المستقبل

### القاعدة:
- استخدم ALLOW فوراً إذا لم يكن هناك تغييرات كود في آخر turn
- لا تعبث: BLOCK فقط لمشاكل حقيقية
```

**مستوحى من:** Codex Plugin's Stop Review Gate hook

## 🔥 القاعدة الذهبية #15: المراجعة العدائية (Adversarial Review)

### اكسر الثقة في التغيير، لا تتحقق منه

```markdown
## Adversarial Review (للمهام الحرجة)

### العقلية:
- لا تفترض أن التغيير صحيح
- ابحث عن أقوى الأسباب لعدم إطلاق هذا التغيير
- لا تعطي نقاطاً للنوايا الحسنة أو الإصلاحات الجزئية

### أسطح الهجوم:
- Auth، permissions، tenant isolation
- فقدان البيانات، التلف، الازدواجية
- سلامة التراجع (rollback)، retries، idempotency
- race conditions، stale state، re-entrancy
- empty-state، null، timeouts
- version skew، schema drift

### معايير النتيجة:
كل finding يجب أن يجيب:
1. ما الذي يمكن أن يحدث خطأ؟
2. لماذا هذا المسار البرمجي معرض للخطر؟
3. ما هو التأثير المحتمل؟
4. ما التغيير الملموس الذي يقلل المخاطرة؟

### لا تبلغ عن:
- أسلوب أو تسمية
- مخاوف تخمينية بدون دليل
- اقتراحات تنظيف منخفضة القيمة

### استخدم:
```xml
<operating_stance>
Default to skepticism.
Assume the change can fail in subtle, high-cost ways until evidence says otherwise.
</operating_stance>

<attack_surface>
Prioritize failures that are expensive, dangerous, or hard to detect.
</attack_surface>

<calibration_rules>
Prefer one strong finding over several weak ones.
If the change looks safe, say so directly and return no findings.
</calibration_rules>
```
```

**مستوحى من:** Codex Plugin's Adversarial Review prompt

## 🔄 القاعدة الذهبية #16: قواعد التفويض للوكلاء (Agent Forwarding)

### كل وكيل هو wrapper رقيق، لا orcestrator

```markdown
## Agent Forwarding Rules (إلزامي)

### عند تفويض مهمة لوكيل آخر:
1. **الوكيل هو wrapper رقيق** - مهمته الوحيدة هي تمرير المهمة للوكيل المتخصص
2. **لا تحل المشكلة بنفسك** - لا تقرأ الملفات، لا تحلل، لا تبحث
3. **مرّر الطلب كما هو** - حافظ على نية المستخدم، لا تعد كتابة الطلب
4. **ارجع النتيجة كما هي** - لا تلخص، لا تفسر، لا تعلق
5. **استدعاء واحد فقط** - استخدم أداة واحدة فقط (استدعاء Bash واحد مثلاً)
6. **إذا فشل الاستدعاء** - أبلغ بالفشل ولا تحاول حل المشكلة بنفسك

### المنع:
- لا تقم بعمل الوكيل المفوَّض له
- لا تفتش على التقدم
- لا تجلب النتائج بنفسك
- لا تلخص المخرجات
- لا تقم بعمل متابعة (follow-up) بنفسك

### مثال صحيح:
```
المستخدم: حقق في فشل الاختبارات
أنا ← codex-rescue (يمرّر الطلب) ← Codex
عند العودة: أعرض stdout كما هو
```

### مثال خاطئ:
```
المستخدم: حقق في فشل الاختبارات
أنا: اقرأ logs، حلل، اكتشف الخطأ
ثم أرسل للوكيل مهمة مختلفة
❌ هذا خطأ - الوكيل قام بعمل المفوَّض!
```
```

**مستوحى من:** Codex Plugin's codex-rescue subagent forwarding rules

## 🔄 القاعدة الذهبية #18: نمط المستشار-المنسّق-العامل (Advisor-Orchestrator-Worker)

### نموذج من 3 طبقات للمهام الكبيرة

مستوحى من [Awesome LLM Apps](https://github.com/Shubhamsaboo/awesome-llm-apps) (129K⭐) الـ AOW pattern للمهام الضخمة جداً.

```markdown
## Advisor-Orchestrator-Worker (للمهام الاستثنائية)

### متى:
- مهمة أكبر من أن يكملها نموذج واحد
- تحتاج أبحاثاً متوازية عبر عدة مجالات
- المستخدم طلب صراحة تنسيق نماذج متعددة

### الطبقات:

1. **🧠 Advisor (مستشار)** - أقوى نموذج للتفكير العميق
   - استراتيجية، تحليل مخاطر، تقييم خطة
   - يُستشار فقط عند نقاط القرار الحرجة
   - **لا ينفذ أبداً** - فقط تفكير وتوجيه

2. **🎯 Orchestrator (منسّق) - أنا**
   - أخطط، أوزّع، أتحقق، أركّب
   - أتحكم في المسار الساخن (hot path)
   - لا أعمل عمل العمال (workers)

3. **⚡ Workers (عمال)** - أرخص النماذج وأسرعها
   - وحدات توليد لا حالة لها (stateless)
   - كل عامل يعزل في مساره الخاص
   - ينفذ المهام الفرعية بالتوازي

### الحلقة (The Loop):
1. **التأطير (Frame)** - حدد التسليم + معايير النجاح (3-5):checkable criteria
2. **التخطيط (Plan)** - قسّم إلى مهام فرعية بمواعيد
3. **مراجعة الخطة (مستشار إلزامي #1)** - المستشار يراجع الخطة
4. **التفويض (Delegate)** - وزّع على العمال Waves متوازية
5. **التحقق من النتائج** - تأكد من الجودة قبل التجميع
6. **مراجعة نهائية (مستشار إلزامي #2)** - قبل التسليم
7. **التجميع (Synthesize)** - ادمج كل شيء

### القيود:
- Wave واحدة بحد أقصى 3 عمال (لتفادي quota)
- استخدام الـ advisor إجباري 2+ مرات
- كل Worker يعزل في (temp dir + minimal env)
- فشل الـ worker → retry مرة واحدة، ثم Escalate
```

## 🔊 القاعدة الذهبية #19: الصدى والتوثيق (Thinking Out Loud / Echo)

### قبل أن تعمل على أي أمر غامض: راجع فهمك أولاً

مستوحى من [Thinking Out Loud](https://github.com/Shubhamsaboo/awesome-llm-apps/tree/main/agent_skills/thinking-out-loud) skill.

```markdown
## Thinking Out Loud / Echo Protocol

### متى:
- المستخدم يملي بصوت طويل غير منظم
- المستخدم يقول "دعني أفكر بصوت عالٍ"
- رسالة فيها تراجعات واستدراكات ("لا، ألغ هذه الفكرة")
- طلب ضبابي أو نصف مكتمل

### البروتوكول:
1. **لا تفعل شيئاً** - لا تعديلات، لا كود، لا خطط
2. **أعد صدى (Echo)** - لخّص فهمك في فقرات قصيرة:
   - ما فهمته من المهمة
   - الاستنتاجات التي استنتجتها أنا (مفصولة عن كلام المستخدم)
   - الأسئلة المفتوحة
   - التراجعات التي لاحظتها
3. **اطلب الموافقة** - المستخدم يصحح 3 سطور
   بدلاً من أن يصحح ساعة من الكود المُنشأ
4. **بعد الموافقة فقط** - ابدأ العمل

### قواعد الصدى:
- لا تضع استنتاجاتك في صوت المستخدم
- أبرز كل تراجع: تبنّ الموقف الأخير وأشر إلى التغيير
- لا تفقد أي شيء (المواضيع الجانبية تُوقف، لا تُحذف)
- لا تعلق على أخطاء الإملاء/النطق
- اسأل قبل الحفظ: لا تحفظ أي شيء بدون موافقة

### لماذا الصدى بدلاً من أسئلة التوضيح فقط؟
- الأسئلة تتحقق مما يشك فيه النموذج.
- الصدى يتحقق مما يعتقده النموذج بثقة - وهذا أخطر.
- المستخدم يتعرف على الخطأ (recognition) أسهل من أن يصححه (recall).
```

## 🎯 القاعدة الذهبية #21: النية مقابل التنفيذ (Intent vs Output)

### هل ما بنيته هو ما طلبه المستخدم فعلاً؟

مستوحى من [Scope Creep Detector](https://github.com/Shubhamsaboo/awesome-llm-apps/tree/main/agent_skills/scope-creep-detector) من Awesome LLM Apps.

```markdown
## Intent vs Output Verification

### قبل تسليم التغيير:
1. **حدد النية (Intent)**:
   - جملة واحدة توضح المطلوب بالضبط
   - مثال: "إصلاح null dereference في parser"
   - مثال: "إضافة retry limit لإرسال webhook"

2. **قارن مع المخرجات (Output)**:
   - هل كل ملف تم تغييره ضروري للنية؟

   - هل التغيير أكبر من اللازم؟

3. **صنّف الانحرافات**:
   - **Scope Creep**: تغييرات أكبر من المطلوب
   - **Unrelated files**: ملفات لا علاقة لها
   - **Dependency additions**: إضافات غير ضرورية
   - **Config/CI changes**: تغييرات تكوين غير مطلوبة
   - **Reformatting**: تغييرات تنسيق فقط

### القرار:
- **Keep**: التغيير ضمن النية وفي محله
- **Split**: افصل التغييرات غير المرتبطة إلى PRs منفصلة
- **Justify**: إذا كان التغيير ضرورياً، برر كتابياً
- **Revert**: إذا التغيير خارج النية تماماً
```

## 🎨 القاعدة الذهبية #25: مهارة Hallmark للتصميم (إلزامية عند طلب التصميم)
